# Folk capability research and Worldview replacement contract

Researched 23 November 2026. This is a product and migration specification, not a claim that every item below is implemented. Sources are Folk's own help center, developer documentation and feature catalog. Private workspace exports, identifiers, schemas and migration counts belong in ignored `data/crm-migration/`, never in this document.

## The model to preserve

Folk separates a global record from its role in a workflow. People and companies exist once; a record may belong to several groups. Native fields describe the record everywhere, while custom fields belong to a particular group. Notes, tasks and interactions attach to the record. Views save a group's presentation, filters, sorting and columns. Flattening everything into tags or a single universal status would lose the user's classification system. [Folk data model](https://help.folk.app/en/articles/9790806-folk-data-model)

Worldview should keep these concepts independently addressable: people, companies, custom objects, groups, memberships, field definitions, field options, field values, views, comments, tasks, interaction events and evidence-backed relationship edges. Preserve original source IDs and raw values. Local aliases and a clearer hierarchy may be added without rewriting the original taxonomy. This is our proposed design, derived from the source model above.

## Improvements specific to Worldview

These are design recommendations, not claims about Folk capabilities.

1. **A relationship map with evidence.** Use explicit people/company/relationship fields as initial edges. Show inferred links as candidates with a visible reason; never silently promote an event attendee or shared employer into “knows.” Clicking an edge should open its source, date and editable meaning.
2. **A clean taxonomy without data loss.** Treat groups, role fields, event attendance, relationship strength, interests and personal labels as separate dimensions. Let saved views combine them. Keep every original group and option until the user intentionally reorganizes it.
3. **One contact, many sources.** Track each connected email/Drive/calendar/import account independently. Exact source IDs establish continuity; email matching creates a possible identity match rather than an unconditional overwrite.
4. **Comments before ceremony.** A contact should be reachable from search, calendar, graph or Reader, with a comment composer immediately available. Show saved/error state, privacy and a way to undo edits.
5. **Reviewable assistance.** External ChatGPT enrichment submits a proposed patch with citations, expected revision and conflicting current values. Approval applies that patch transactionally and records its history. Cloud AI does not need to be enabled in Worldview.
6. **Source-aware integrations.** Calendar, email, Drive, Happenstance, Luma and Partiful need separate adapters and credentials/import paths. Having a URL field or CSV uploader is not evidence of a live integration. State what was actually read, when it last succeeded and what remains unconnected.

## Migration audit and actual adapter coverage

The read-only connector was used to retrieve all accessible people, companies, groups, notes and tasks through terminal cursors. People and companies were queried in complementary empty/nonempty name streams so unnamed records were retained. Repeated IDs across pages were consolidated by source identity; original raw pages remain available privately. Group schemas, select option order, pipelines, memberships, source authors and visibility were retained. A group may contain both people and companies.

The adapter in `server/crmFolk.ts` is pure: it maps the private export to CRM records and returns counts, issues and completeness. It preserves original entity IDs, raw payloads, group-specific fields, null/unknown values, member assignments, recurrence, task completion and note parents. Deterministic generated IDs cover memberships, fields/options and relationship edges. It does not write to Folk or the live Worldview store. Persistence, conflict handling and backups belong to the command store.

The connector does not expose arbitrary saved table layouts, group access lists, campaigns, template inventories or source attachments as downloadable assets. Pipeline metadata is available, but it is insufficient to recreate every saved column arrangement/filter. Raw note markup and attachment metadata do not mean attachment binaries have been downloaded. Those gaps must be represented honestly.

Both advertised interaction-list tools failed with JSON-RPC `-32602`, reporting that the tool did not exist. No interaction detail/body requests were made. Record-level approximate counts and dates were preserved, but those summaries are not migrated interaction events. The private manifest marks interaction history incomplete and retains the exact capability errors. Empty imported history must not be described as “no previous interactions.”

## Read-only REST route for missing interaction history

The current official beta endpoint is `GET https://api.folk.app/v1/interactions` with required `entity.id=<source ID>` and `timeframe=past|upcoming`. Its response wraps records under `data.items`; `data.pagination.nextLink` identifies subsequent pages. Omit `importedTypes` to include all imported types along with manual logs. An empty `importedTypes` value selects manual logs only. Full detail/body retrieval is a separate operation and is unnecessary for a list-level migration. [List interactions](https://developer.folk.app/api-reference/interactions/list-interactions.md)

The REST API uses a user-created bearer API key from Folk workspace Settings → API; authenticated connector access does not expose that key. The published catalog gates REST access to paid tiers. Store a user-provided key locally in a credential store, never in source control or chat, and validate it with read-only operations. [Authentication](https://developer.folk.app/api-reference/authentication.md), [Quick start](https://developer.folk.app/guides/quick-start.md), [Feature catalog](https://www.folk.app/pricing)

An exporter should enumerate every accessible person/company/object for both timeframes, checkpoint after each page, retain privacy and entity associations, deduplicate event IDs without discarding those associations, and mark complete only after every terminal page succeeds. Validate next-link origin/path before forwarding credentials. The documented limits are 600 requests/minute/user and 20 requests/2 seconds; honor server headers and `Retry-After`. [Rate limits](https://developer.folk.app/api-reference/rate-limits.md)

For continued synchronization, webhooks need signature validation over the original body, deduplication and quick acknowledgment followed by durable processing. Deliveries are not guaranteed to arrive in order. This is a separate deployment concern, not necessary for a one-time private migration. [Webhook handling](https://developer.folk.app/webhooks/handle-deliveries)

## Verification required before calling it a complete replacement

- Reconcile terminal-page counts, raw originals, membership/field option references and unnamed records after import; no private data in Git.
- Reimport the same backup twice without duplicates, then import newer source data after local edits and verify conflicts are reviewed rather than overwritten.
- Save/edit/reload a private comment and reply; preserve author, visibility, attachments and parent references.
- Move a pipeline card and confirm only that group's select value changes; verify history/undo and another group's distinct status remain intact.
- Import a calendar event twice, edit/cancel it at source, and confirm stable identity and cancellation handling. Do not infer confirmed attendance.
- Confirm source history gaps remain visible until migration truly succeeds. An approximate interaction count is not a substitute for its events.
- Verify a cited enrichment proposal can be reviewed and applied without enabling cloud AI or silently making outside writes.
- Verify existing writing, reading, Obsidian imports and the 3D world still operate. The CRM shares the application shell and local durability model.

Sending, scheduling, billing, a full native mobile app and production multi-user permissions require their own end-to-end validation. A local draft surface alone does not establish those capabilities.
